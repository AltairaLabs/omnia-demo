# Memory Galaxy corpus generator

Generates the Larkmere Mutual memory Galaxy, the synthetic corpus the
memory-seeder replays into every memory tier: what members talk about (user
tier), what each agent learned about a member (user_for_agent), what the agents
learned across cases (agent), and what the society knows (institutional, as a
knowledge graph).

The text is generated by a model, not filled into templates: templated memories
read as synthetic the moment one is opened in the Galaxy. Generation is paid for
**once**:

- Every model call is cached in [`cache/`](cache/), under the SHA-256 of its
  request (model, system prompt and user prompt), and the cache is committed.
- A run reads the cache and calls the model only for prompts it has never seen.
  Rebuilding the corpus from a fresh checkout costs nothing:
  `go run ./demos/memory-galaxy --offline`.
- Each batch of memories is its own prompt, so raising `--scale` only generates
  the new batches. Editing one subtheme in `taxonomy.yaml` regenerates only that
  subtheme's prompts.

The output goes to `demos/memory-seeder/fixtures/larkmere-galaxy/`, which the
seeder image embeds (`--fixture larkmere-galaxy`). The chart's `galaxy`
component seeds it; see the chart README.

## What's in it

[`taxonomy.yaml`](taxonomy.yaml) is the spec: six consent categories, their
themes and weighted subthemes, which agents see each one, how many memories
each tier gets per unit of weight, and the institutional knowledge graph
(products, claim types and procedures, with `covers`, `governs`, `follows` and
`about` edges).

It plants three findings, so the Galaxy has something to show:

1. **A knowledge gap.** Members talk about flood more than anything else in the
   location category, and the institutional tier holds almost nothing on it.
   In the graph, the flood claim type is covered but no procedure governs it.
2. **Tribal knowledge.** The claims agent learns a workaround for storm claims
   with no photos (the Met Office record plus a roofer's invoice) that no
   procedure covers: a dense agent-tier cluster with no institutional
   counterpart.
3. **A rising theme.** Cost-of-living arrears outweigh everything else in the
   context category. The memory API takes no write date, so this shows as
   volume, not recency.

The committed corpus is scale 7 (the default): 9,912 memories (6,552 user,
2,184 user_for_agent, 1,176 agent), plus 954 institutional items and 428
edges, about 10.9k points in the Galaxy. Scale 1, the review sample, is 1,416
memories plus 150 items and 74 edges.

## Running it

Generation needs the Foundry (Azure OpenAI) account, which is keyless and takes
calls only from the AKS subnet. omnia-azure opens it to this machine for the
run and closes it again:

```bash
make -C ../omnia-azure foundry-open     # your IP + Cognitive Services OpenAI User
go run ./demos/memory-galaxy --endpoint "$(jq -r .endpoint ../omnia-azure/.foundry-open.json)"
make -C ../omnia-azure foundry-close
```

`--dry-run` prints the counts and how many prompts are not cached, and calls
nothing. Commit `cache/` and the fixture together.

The review sample (352 prompts, gpt-5.4-mini) took about three minutes and
well under a dollar; scaling it to 7 (891 more prompts) took eight. Seeding still embeds the corpus each time it runs
(memory-api computes the vectors), which is cents.

## Scaling up

```bash
go run ./demos/memory-galaxy --dry-run --scale 25    # ~35k memories: see what's not cached
go run ./demos/memory-galaxy --endpoint ... --scale 25
```

The memory API caps one batch-ingest request at 5,000 items; past that the
seeder would need to split the institutional graph.
